# Implementation record — 2026-07-30 incident fixes (v0.4.278 → v0.4.279)

Companion to `incident-2026-07-30-duplicate-daemon-stage1.md` (root cause) and
`…-stage2-design.md` (design). This records what was actually built, what was proven, and the two
places reality corrected the design.

## Corrections to the earlier docs — read these first

1. **Fix 1's first attempt was wrong and I shipped it.** The design said "wrap the spawn in
   try/catch". `child_process.spawn` does **not** throw synchronously on an unresolvable interpreter:
   it returns a child with `pid === undefined` and *then* emits `'error'`, which with no listener
   becomes an **uncaught exception**. A try/catch cannot see it. v0.4.278 shipped the try/catch-only
   fix and the watchdog died the same way on its very next respawn — caught by the live check, not by
   the tests. The real guard is `child.on('error', …)` plus an `uncaughtException` handler; that is
   v0.4.279.
2. **The ENOENT trigger is NOT the bun symlink.** Stage 1 inferred that the daemon's
   `~/.bun/bin` provisioning made the binary transiently unresolvable. Evidence contradicts it:
   the recurrence named the fully-resolved `/home/ubuntu/.bun/bin/bun`, a file unchanged since
   May 25. **The trigger remains unexplained.** Leading (unproven) hypothesis, recorded in the code:
   the watchdog's own `SIGCHLD` reaper `waitpid()`s the new child before libuv can read its status —
   the reaper's own comment already warns that stealing child status breaks callers. Since the trigger
   is unknown, *surviving* it is the requirement.
3. **1ede4baa's orphaning is explained** (owner, via @hermesbus): tonight's recovery was partly a
   Hermes relaunch that started a **cold** chat lane while the old lane's pane stayed alive. A cold
   bridge recovery orphans the previous chat-lane pane — no reaping, no handoff.

`writeJsonFile` is now the single atomic JSON-state primitive. Five sites already hand-rolled
tmp+rename because it wasn't (`session-harness.ts` — author of the leftover `.tmp` that flagged this,
`effort-scope.ts`, `access.ts`, `daemon.ts` ×2). They are left alone deliberately: `access.ts` has a

## Test-isolation traps hit (both would have looked like production bugs)

- `mock.module('./proc.ts')` registers **process-wide** and bun shares a process across files — a mock
  answering every `exec()` silently failed 8 `status-card` tests. Fixed by delegating to the real
  module for any pane the file didn't script.
- `_resetForTest({ groupChatId })` leaves the topics store in **topic mode** for every later file.
  Fixed with an `afterAll` restore, matching `bus-statedir.test.ts`'s pattern.
- `sessionForPane` caches pane→sid process-wide, so reusing a pane id hands the next test the previous
  test's session. Each test now uses a distinct pane id.

## Known gap, stated rather than papered over

A chat lane whose binding is **already** lost cannot be identified from pane stamps alone (a lane is
defined by its `dmChat` entry, and cwd is not a reliable signal). 4b therefore skips bound lanes and
cannot self-heal an already-unbound one; 4a is what stops the binding being lost in the first place.
Tonight's unbound lane was repaired by hand.
