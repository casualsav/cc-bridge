# Implementation record — 2026-07-30 incident fixes (v0.4.278 → v0.4.279)

Companion to `incident-2026-07-30-duplicate-daemon-stage1.md` (root cause) and
`…-stage2-design.md` (design). This records what was actually built, what was proven, and the two
places reality corrected the design.

## Corrections to the earlier docs — read these first

1. **Fix 1's first attempt was wrong and I shipped it.** The design said "wrap the spawn in
   try/catch". `child_process.spawn` does **not** throw synchronously on an unresolvable interpreter:
   it returns a child with `pid === undefined` and *then* emits `'error'`, which with no listener
   becomes an **uncaught exception**. A try/catch cannot see it. v0.4.278 shipped the try/catch-only
   fix and the watchdog died the same way on its very next respawn — caught by the live check, not by
   the tests. The real guard is `child.on('error', …)` plus an `uncaughtException` handler; that is
   v0.4.279.
2. **The ENOENT trigger is NOT the bun symlink — it is a DELETED CWD.** Stage 1 inferred that the
   daemon's `~/.bun/bin` provisioning made the binary transiently unresolvable; the recurrence
   contradicted that by naming the fully-resolved `/home/ubuntu/.bun/bin/bun`, a file unchanged since
   May 25, and this doc recorded the trigger as unexplained. It is explained now, and the SIGCHLD-reaper
   hypothesis recorded here is withdrawn: **under Bun, a process whose cwd has been deleted cannot spawn
   anything at all** — every spawn fails `ENOENT … posix_spawn '<binary>'`, PATH-resolved *and* absolute,
   while `process.cwd()` keeps returning the stale path so the process looks healthy to itself.
   *Measured*, re-runnable: `bun scripts/deleted-cwd-spawn.ts`. That the 04:18:30 watchdog ENOENT was
   this is **inferred but strong** (that watchdog had been started by a hook running in a
   `/tmp/predict-replay-*` scratch dir the harness later deleted, and the same mechanism was observed
   directly on the daemon side minutes later); the daemon failing on bare `tmux` from a deleted cwd is
   **observed fact**. The survival machinery (`child.on('error')` + `uncaughtException`) stays — it is
   what keeps an unexplained *future* launch failure non-fatal — but the class is now prevented, not
   merely survived. See "Second outage, same night" below.
3. **1ede4baa's orphaning is explained** (owner, via @hermesbus): tonight's recovery was partly a
   Hermes relaunch that started a **cold** chat lane while the old lane's pane stayed alive. A cold
   bridge recovery orphans the previous chat-lane pane — no reaping, no handoff.

## Test-isolation traps hit (both would have looked like production bugs)

- `mock.module('./proc.ts')` registers **process-wide** and bun shares a process across files — a mock
  answering every `exec()` silently failed 8 `status-card` tests. Fixed by delegating to the real
  module for any pane the file didn't script.
- `_resetForTest({ groupChatId })` leaves the topics store in **topic mode** for every later file.
  Fixed with an `afterAll` restore, matching `bus-statedir.test.ts`'s pattern.
- `sessionForPane` caches pane→sid process-wide, so reusing a pane id hands the next test the previous
  test's session. Each test now uses a distinct pane id.

## Second outage, same night — the inherited-cwd class (v0.4.281)

The fleet went down twice MORE after the fixes above, from a cause none of them touch. Both times the
whole roster read down, spawns failed and bus asks were refused; both times the daemon's log said
`ENOENT posix_spawn 'tmux'` while `/usr/bin/tmux` sat there and PATH contained `/usr/bin`.

**The chain, observed** (owner read `/proc` and the daemon log directly). Another project's replay
harness ran `claude -p` subprocesses from `/tmp/predict-replay-*` scratch dirs. Their SessionStart hooks
ran `ensure-daemon`, which — during the deploy restarts above — found the daemon down and started
**watchdogs standing in those scratch dirs**. The harness then deleted the dirs. Every process in the
chain inherits its launcher's cwd, so each poisoned watchdog spawned a daemon in the same dead dir, and
that daemon could not exec `tmux`: its pane scan returned 0 panes on every tick, so the entire fleet
read down. Self-perpetuating, which is what made it look like an epidemic: each blind window made `tg`
calls see the daemon as down and nudge yet another watchdog into existence from yet another doomed dir.
Instances observed: watchdogs 3462325+3462326 and daemon 3463167 in a deleted
`/tmp/predict-replay-2if01r_h`; after those were killed, watchdog 3476313 + daemon 3476335 in a deleted
`/tmp/predict-replay-v6j8qfl4`. **A third survivor was found during this work and is recorded below.**

**Why Fix 2 was needed at all, given 4a shipped hours earlier.** 4a's inconclusive-scan skip counted
only `topics` rows, and it guards only the GC tick. Two paths went around it: the **event path**
(`PaneWatcher` declared death on a failed capture → `closeTopicForPane` → the lane reap), which is what
the log shows at 04:33:43 (`daemon: pane %330 died` for the owner's live chat lane), and a store holding
a **lane but no rows**, which made `listTopics().length` zero and the guard a no-op. Both now require
positive evidence: `paneLiveness` returns `'unknown'` when tmux cannot be reached and every destroyer
treats that as "do nothing", and the guard counts lanes + the anchor as session records.

## Known gap, stated rather than papered over

A chat lane whose binding is **already** lost cannot be identified from pane stamps alone (a lane is
defined by its `dmChat` entry, and cwd is not a reliable signal). 4b therefore skips bound lanes and
cannot self-heal an already-unbound one; 4a is what stops the binding being lost in the first place.
Tonight's unbound lane was repaired by hand.
